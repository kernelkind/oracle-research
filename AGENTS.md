# Oracle MVP Rules

- For prompt experiments, use `python3 sse_multivector/experiment.py` and read the workflow in `sse_multivector/model-runner.md`. The supported commands are `prepare`, `run`, `show`, `revise` and `review`. Do not hand-build rendered batches, coordinate waves, total usage, construct comparison/review JSON, or add experiment-specific execution scripts. Generic variables support arbitrary prompting tasks; title/mask adapters reuse production preparation and validation.
- `prepare --from EXISTING --prompt FILE --prompt-id VERSION` inherits cases/settings and uses the saved outputs as baseline without rerunning it. Only `run` performs inference, and it requires task/spending authorization. Frozen inputs/settings cannot change during a run. Use `show --case ID` for exact evidence instead of loading whole result files into context. Use `revise` against the last approved prompt for a versioned, full-context delta.
- Identical requests are reused across runs. Prepare a new experiment with `--repeat` only for an intentional independent trial; reused answers are not new samples. Keep related experiments under the same history root, preserve receipts, and distinguish mechanical checks, agent assessments and actual user decisions. Never invent user approvals. Experiment directories are ignored artifacts; keep reusable prompts/specs and maintained docs outside them.
- Independent prompt cases continue after isolated failures. Automatic retries are provider-only, with at most two total attempts per case across resumes; local timeouts, validation errors and unknown causes must not be retried. Reserve spending for retries and use `run --max-new-attempts N` to bound newly sent calls. There is no blanket experiment retry override. An approved workflow-code update can resume an existing experiment with `--runner-upgrade-reason "..."`, recording code/provenance changes without editing frozen inputs/settings or old receipts.
- The general pi-ai transport remains `sse_multivector/run-model.sh` for non-experiment callers. Production extraction `extraction_pipeline.py run` / `subjects`, `claim_exec.py` and the frozen comparison adapter retain their contracts. The old public saved-batch `prompt CONFIG`, `masks` and `revise-prompt` paths are retired. Import historical results through `experiment.py prepare --spec ... --import-config ...` with verified input mappings; do not rerun baselines or use archived job commands for new calls.
- Do not commit blobs or experiment data, including source corpora, model responses, generated vectors and run outputs. Keep reusable code, tests, prompts and maintained documentation distinct from those artifacts, even when they share a directory. Keeping data out of Git does not authorize deleting it or rewriting existing history.
- After completing a task and before ending your turn, reconsider the broader goal in light of the results and remaining uncertainties. Proactively recommend the most useful next step and briefly explain why it is warranted. Suggest it without beginning it; wait for explicit approval. If no useful next step is justified, say so rather than inventing more work.
- When presenting any command for the user to paste, use short paths and explicit `\` line continuations when wrapping. Never split a file path or other shell argument across lines. Put the complete command, including any required working-directory change, in one shell code block so it can be pasted without editing; continuation backslashes must be the last character on their lines. For delta diffs, keep the `nix run nixpkgs#delta -- --paging=always` invocation on one line.
- Label every prompt shown to the user with an explicit version ID (for example, `MPv3.9`), including drafts, experimental variants, and links to prompt files. Report draft/tested/frozen status separately from the ID.
- The lifetime monetary budget for the entire oracle MVP is **$1,000 USD**, replacing the previous $500 ceiling. This is a hard ceiling, not a target or a per-model allowance.
- The ceiling includes every paid resource used by the effort, including CPU and GPU rentals, storage, transfers, failed or interrupted runs, calibration, evaluation, diagnostics, and confirmation work.
- Before any action that can incur a charge, read `budget-ledger.json`. Do not spend money when the ledger is missing, internally inconsistent, or contains an unknown value needed to prove admission. Treat the ledger as stale whenever an active paid resource or an incurred charge is not represented and reconciled.
- A paid action is admissible only when `actual spend + existing outstanding commitments + the action's maximum charge + reserved remaining-work budget <= $1,000`. The existing commitments value excludes the proposed action during this check; after approval, add the action's maximum charge to the ledger before accepting the paid commitment.
- The spending code and `budget-ledger.json` enforce the $1,000 lifetime cap. The approved future-work reserve is $0: no amount is currently earmarked for fine-tuning or another stage. Recorded spending and outstanding commitments still count; calibration has no separate spending cap.
- User-requested OpenRouter work with a rough estimated total cost of $1 or less is authorized without another spending-approval question or a provider-side spending cap. Make a quick judgment; do not run calculations or spend time producing a detailed estimate. Ask before work estimated to exceed $1. This standing approval covers the requested task, not unrelated work, and does not waive the lifetime ceiling or ledger accounting.
- Other paid actions require the user's explicit approval of their maximum charge and an external provider-side termination limit that enforces that maximum. A software estimate or process timeout alone is insufficient for those actions.
- Update and commit `budget-ledger.json` before accepting a paid commitment and again after reconciling its actual charge.
- Plane work items must represent work that is understood, certain, and ready to execute. Do not create cards for hypothetical branches, conditional future work, or unresolved implementation choices. Create the work item only when its trigger has occurred and its scope is known.
